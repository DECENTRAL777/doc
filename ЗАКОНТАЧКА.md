# Законтачка

Собственный закрытый P2P-оверлей. Статус: черновик LAN MVP. Внутренний транспорт
— **UDP/IPv4**, криптографическое соединение — Noise, маршрутизация — ограниченная
Kademlia. QUIC и libp2p (включая их PeerId, Relay, DCUtR, GossipSub и
протокольные идентификаторы) не являются зависимостями или целью совместимости.

## Состав первого MVP

1. Узел загружает `network_id`, свои Ed25519/X25519 ключи, подписанный оператором
   сертификат, доверенный Ed25519 issuer key, последний подписанный список отзывов
   и несколько адресов seed (`IPv4:port`).
2. Соединение с seed устанавливается по
   `Noise_XX_25519_ChaChaPoly_SHA256`. Библиотека Noise выбирается только после
   запуска в GraalVM Static Native Image.
3. Внутри защищённого рукопожатия стороны предъявляют сертификаты, связывают
   статические Noise X25519 ключи с Ed25519 NodeId и подписывают стенограмму
   Ed25519-ключами. До проверки допуска они не обрабатывают прикладные команды.
4. Узлы обмениваются защищёнными `PING` и `FIND_NODE` и пополняют локальную
   таблицу только проверенными NodeId. Полученный адрес — лишь подсказка: с новым
   пиром проводится полный handshake.
5. Независимые короткие сообщения получают подтверждение или ограниченный повтор.
   Дубликат не передаётся обработчику повторно. Доставка при долгом отключении и
   общий упорядоченный поток не входят в первый MVP.

Шифрование Noise **сквозное между конечными узлами**. Когда появится relay, он
будет пересылать зашифрованные кадры конечной сессии A↔B. Задачи хранения
сообщения для отключённого B здесь нет: для неё впоследствии потребуется отдельный
проект, а не предположение о постоянном живом сеансе.

## Идентичность и допуск

`NodeId` получается из Ed25519 public key; X25519 Noise key — независимая пара.
Операторский issuer-ключ Ed25519 находится вне агентов. Его подпись на сертификате
связывает оба узловых ключа с одной сетью и сроком действия. Проверка включает
версию, `network_id`, срок, подпись issuer, соответствие NodeId и X25519 ключа
рукопожатию, Ed25519-подпись стенограммы и локально известные отзывы. Сборник
адресов seed сам по себе не является списком допущенных ключей.

Подписанный список отзывов хранится с наибольшей принятой версией; меньшая версия
не применяется. По факту получения отзыва уже установленный сеанс отозванного
узла закрывается. **Что делать со старыми отзывами при разделении сети пока не
определено** и требует отдельного решения до эксплуатации. Первые LAN-тесты
проверяют только поведение с полученным актуальным списком.

## UDP-кадры и Noise

Длина кадра не превышает 1200 байт **включая заголовок и теги**; IP-фрагментацию
не используем. Внешний заголовок несёт маркер, версию, тип, `network_id`,
идентификатор сессии и длину. Noise-handshake ограничен по времени, числу попыток,
размеру и количеству одновременных состояний. До завершения handshake никакие
данные не считаются авторизованными.

После handshake пакеты имеют уникальный номер в рамках нового сеанса, AEAD
аутентифицирует заголовок и содержимое. ACK и повторы ограничены; получатель
держит окно номеров для подавления дубликатов. Сообщения **не упорядочиваются**
глобально: `FIND_NODE` сопоставляется со своим запросом по request ID. При
переподключении используется новый идентификатор сеанса и новые ключи, старые
шифротексты не должны приниматься.

Точный заголовок v1, кодирование полей и подписываемые байты зафиксированы
черновиком [Малявы](МАЛЯВА.md). До независимых тестовых векторов он не считается
замороженным. Предел 1200 байт исключает большие объекты из первого протокола.

## Минимальная Kademlia

Kademlia отвечает **только за поиск узлов**, не за авторизацию или хранение.
Расстояние между 32-байтными NodeId — XOR. Таблица ведётся по ограниченным
XOR-корзинам и хранит только проверенных пиров, их последние известные IPv4:port
и время наблюдения. Первый LAN MVP реализует:

- `PING`/`PONG` для проверки живости и времени ответа;
- `FIND_NODE`/`NODES` для поиска ближайших известных NodeId;
- проверку сертификата перед добавлением результата в таблицу; адрес из чужого
  ответа нельзя объявить проверенным без подключения к самому узлу.

Публикация произвольных значений, provider records и широковещательная тема в
DHT не нужны. В трёхузловом стенде A и C знают только seed B; A находит C через
ответ B, проверяет C напрямую и выполняет ping. Разрыв соединения с B не должен
разрывать уже найденное прямое соединение A↔C.

## Отдельный этап: NAT и relay

После LAN-gate узел сможет узнать наблюдаемый внешний IPv4:port, согласовать
встречные UDP-пакеты и предпочесть прямой маршрут. При невозможности прямого
соединения доверенный relay пересылает пакеты конечной Noise-сессии с квотами
по трафику, числу сеансов и времени. Relay видит адреса, время и объём, но не
payload. Отказ одного relay переключает на другой, если он доступен обоим
концам. Ни hole punching, ни relay не обещаны первым LAN MVP.

## Эксплуатационные ограничения и проверка

- Приёмник проверяет версию, сеть и размер до выделения буфера под сообщение;
  отклоняет неопознанные типы и не сообщает постороннему детали допуска.
- Лимиты на состояния handshake, rate per source, повторы, размеры корзин и
  число исходящих соединений фиксируются до WAN/NAT gate.
- Ошибки рукопожатия, RTT ping, найденные узлы и тип пути наблюдаемы без записи
  приватных ключей и plaintext полезной нагрузки.
- Испытания: три LAN-узла, просроченный/неверный/отозванный сертификат, потеря
  и повтор UDP-кадра, подмена заголовка или подписи, перезапуск с сохранёнными
  ключами и отзывами, запуск нативного исполняемого файла.

**Открыто:** поведение при устаревшем списке отзывов, состав anti-amplification
защиты для публичных адресов, точные значения тайм-аутов и квот, а также схема
UDP hole punching/relay после LAN-gate.
