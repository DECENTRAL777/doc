# Законтачка

Законтачка — P2P-подсистема проекта. Она устанавливает защищённые соединения между
доверенными узлами, находит участников через Kademlia, преодолевает NAT и доставляет
сообщения напрямую либо через ретранслятор.

Статус: черновик спецификации MVP.

## 1. Цели

1. Подключить допущенный узел к закрытой P2P-сети по небольшому списку адресов
   начальных узлов.
2. Проверить идентичность и допуск удалённого узла до обмена прикладными данными.
3. Обеспечить проверку связи ping/pong между двумя допущенными узлами при наличии NAT.
4. Сначала пытаться установить прямой канал, затем использовать ретранслятор без потери
   функциональности.
5. Поддержать адресную доставку сообщений, команд C2, результатов и служебных
   событий.
6. Не привязывать формат протокола при передаче к одному языку или одной реализации
   `libp2p`.

## 2. Не-цели

- анонимность участников;
- доступ из публичной сети без сертификата;
- гарантия прямого P2P-соединения при симметричном NAT или запретительном межсетевом
  экране;
- использование DHT как базы данных со строгой согласованностью;
- византийский консенсус;
- сокрытие IP-адресов от начальных узлов и ретрансляторов.

## 3. Роли

| Роль           | Ответственность                                                         |
|----------------|-------------------------------------------------------------------------|
| Обычный узел   | Входит в P2P-сеть, ищет пиры, отправляет и принимает сообщения          |
| Начальный узел | Публикует стабильные адреса libp2p (multiaddr) для первого входа в сеть |
| Ретранслятор   | Принимает резервирования Circuit Relay v2 и ретранслирует трафик        |
| Оператор       | Выдаёт допуски и публикует подписанные управляющие события              |

Роли `bootstrap` и `relay` не дают права оператора. Допустимые роли и ограничения
узла перечисляются в сертификате допуска.

## 4. Идентичность и ключи

Каждый узел имеет как минимум две независимые пары ключей:

| Ключ      | Назначение                                                                |
|-----------|---------------------------------------------------------------------------|
| `Ed25519` | `PeerId`, подпись сообщений и доказательство владения ключом идентичности |
| `X25519`  | Получение E2E-зашифрованных сообщений через HPKE                          |

`Ed25519` не используется для шифрования. Преобразование ключа `Ed25519` в
`X25519` в MVP запрещено: ключи генерируются и ротируются независимо.

Операторский корень доверия использует `ML-DSA-65`. Автономный корневой ключ
подписывает делегирование оперативного операторского ключа; оперативный ключ
подписывает сертификаты допуска, отзывы и управляющие события. Проверяющий узел
ДОЛЖЕН построить цепочку до настроенного корневого ключа и проверить область
действия делегирования.

## 5. Сетевой стек

Базовый стек MVP:

| Функция                    | Протокол                                          |
|----------------------------|---------------------------------------------------|
| Идентичность               | PeerId libp2p на основе `Ed25519`                 |
| Основной транспорт         | QUIC                                              |
| Резервный транспорт        | TCP + Noise, если доступен в выбранной реализации |
| Поиск узлов                | Kademlia DHT в режиме сервера или клиента         |
| Определение достижимости   | AutoNAT                                           |
| Преодоление NAT            | Circuit Relay v2 и пробивание NAT через DCUtR     |
| Проверка живости           | libp2p Ping                                       |
| Широковещательная доставка | GossipSub с закрытым пространством имён тем       |
| Прикладные сообщения       | Версионируемые потоковые протоколы проекта        |

Собственные идентификаторы протоколов, кадрирование, типы данных при передаче и
лимиты централизованно определяет [Малява](МАЛЯВА.md). Законтачка задаёт поведение
P2P-сети, но не дублирует схемы сообщений.

## 6. Закрытая P2P-сеть

Изоляция сети строится на нескольких уровнях:

1. У каждой сети есть случайный `network_id` размером не менее 128 бит.
2. DHT и GossipSub используют пространство имён, производное от `network_id`.
3. После установки защищённого транспортного соединения libp2p каждый пир проходит
   прикладное рукопожатие `/decentral777/{network_tag}/auth/1.0.0`.
4. До успешного рукопожатия пир НЕ ДОЛЖЕН получать доступ к DHT, резервированию
   Circuit Relay v2, темам C2 и служебного состояния или прикладным потоковым
   протоколам.
5. Модуль допуска соединений закрывает соединение при просроченном, отозванном или
   неподходящем сертификате.

Один предварительно распределённый сетевой ключ МОЖЕТ
использоваться как дополнительная защита от сканирования, но не заменяет
персональные сертификаты и отзыв узлов.

## 7. Сертификат допуска

Сертификат связывает `network_id`, PeerId, публичные ключи узла, роли, полномочия,
срок действия и серийный номер. Его подписывает делегированный операторский ключ
`ML-DSA-65`. Каноническая схема сертификата находится в [Маляве](МАЛЯВА.md), а
жизненный цикл ключей и отзыв описывает [Ксива](КСИВА.md).

Проверка сертификата включает:

1. проверку версии и `network_id`;
2. проверку допустимости времени с ограниченным расхождением часов;
3. проверку связи `peer_id` с `identity_key`;
4. проверку подписи и цепочки делегирования до автономного корневого ключа;
5. проверку серийного номера по актуальному состоянию отзывов;
6. проверку требуемой роли для запрошенного идентификатора протокола.

## 8. Подключение узла

### 8.1 Начальная конфигурация

Для первого запуска узлу нужны:

- `network_id`;
- публичный корневой ключ `ML-DSA-65` оператора;
- собственные ключи и сертификат допуска;
- минимум два адреса multiaddr начальных узлов в рабочей конфигурации;
- локальная политика хранения ключей.

### 8.2 Последовательность первичного подключения

1. Агент загружает ключи и проверяет собственный сертификат.
2. Агент случайным образом выбирает адреса начальных узлов и подключается с
   увеличиваемой задержкой повторов.
3. Транспорт libp2p взаимно подтверждает владение ключами идентичности.
4. Пиры обмениваются цепочкой сертификатов, одноразовым случайным значением и
   подписанной стенограммой рукопожатия.
5. Каждая сторона проверяет допуск и актуальное состояние отзывов.
6. Узел выполняет первичное заполнение Kademlia и добавляет в таблицу маршрутизации
   только допущенных пиров.
7. AutoNAT определяет внешнюю достижимость узла.
8. Недоступный снаружи узел резервирует минимум один ретранслятор; рабочий профиль
   СЛЕДУЕТ настраивать минимум на два независимых ретранслятора.
9. Узел публикует подписанную запись пира с актуальными адресами и сроком жизни.

Начальный узел не выдаёт доверие. Его компрометация может нарушить доступность или
подменить список адресов, но не должна позволить выдать действительный сертификат.

## 9. Преодоление NAT

Алгоритм установления соединения:

1. Использовать известные публичные и наблюдаемые адреса назначения.
2. Одновременно попытаться установить соединение по подходящим адресам.
3. Если узлы нашли друг друга через ретранслятор и поддерживают DCUtR, попытаться
   согласованно пробить NAT.
4. После успешного прямого соединения предпочесть его каналу через ретранслятор.
5. Если прямое соединение и пробивание NAT не сработали, сохранить поток через
   ретранслятор.

Ретранслятор является обязательным резервным путём, а не исключительной аварийной
функцией.
Следовательно, требование «NAT не мешает ping/pong» означает достижимость через
прямой или ретранслируемый путь при условии, что хотя бы один ретранслятор доступен
обоим узлам и исходящие соединения разрешены.

Ретранслятор ДОЛЖЕН применять лимиты резервирований, соединений, полосы и
длительности. Ретранслируемая прикладная полезная нагрузка остаётся
E2E-зашифрованной; ретранслятор видит
метаданные соединения, объём и время трафика.

## 10. Поиск узлов

Kademlia используется только для маршрутизации к пирам и поиска служебных записей
поставщиков.
Она НЕ ДОЛЖНА считаться источником авторизации или строгой истины.

- Таблица маршрутизации содержит только узлы с действующим допуском.
- Полученные записи проверяются до добавления в таблицу.
- Запись пира подписывается ключом идентичности и имеет ограниченный TTL.
- Просроченные адреса удаляются независимо от присутствия PeerId в DHT.
- Значения DHT имеют строгий лимит размера и проверяются до сохранения.
- Собственные пространства имён DHT и GossipSub предотвращают случайное смешение
  сетей.

## 11. Ping/pong MVP

Ping/pong использует стандартный libp2p Ping после успешной авторизации соединения.
Агент измеряет RTT и записывает тип пути: `direct`, `hole-punched` или `relayed`.

MVP считается работоспособным, если:

1. два допущенных узла находят друг друга через DHT;
2. ping проходит в одной LAN;
3. ping проходит между двумя обычными домашними NAT;
4. при невозможности пробить NAT ping проходит через ретранслятор;
5. неизвестный, просроченный и отозванный узлы не могут использовать DHT и ping;
6. перезапуск начального узла после заполнения таблиц маршрутизации не разрывает уже
   найденные маршруты;
7. метрики различают прямой и ретранслируемый пути.

## 12. Прикладные сообщения

При адресной передаче полезная нагрузка шифруется для публичного ключа `X25519`
получателя через HPKE. Транспортное шифрование защищает отдельное соединение, но не
заменяет E2E-шифрование при ретрансляции или доставке с промежуточным хранением.
Конверт подписывается ключом `Ed25519` отправителя.

Получатель ДОЛЖЕН проверить сеть, срок, сертификат отправителя, подпись и защиту от
повторного воспроизведения до передачи полезной нагрузки приложению. `message_id` не
должен быть единственным механизмом такой защиты: хранится ограниченное окно
последовательностей и одноразовых значений отправителя. Схему конверта при передаче,
подписываемые данные, контекст HPKE и коды подтверждения задаёт [Малява](МАЛЯВА.md).

Управляющие события имеют отдельную схему и проверяются по правилам
[Положняку](ПОЛОЖНЯК.md). Они не получают операторские полномочия только
из-за доставки через служебную тему.

## 13. Локальный API агента

Агент предоставляет версионируемый API gRPC через доменный сокет Unix. Локальный
интерфейс TCP допустим на системах без UDS при обязательной локальной
аутентификации.

Минимальные операции:

- получить `PeerId`, роли и состояние допуска;
- вывести список соединений и тип каждого пути;
- найти пир;
- выполнить ping;
- отправить адресное сообщение;
- подписаться на разрешённую тему;
- получить состояние DHT, ретрансляторов и управляющего контура;
- перечитать сертификат без перезапуска.

API по умолчанию НЕ ДОЛЖЕН слушать внешний сетевой интерфейс.

## 14. Хранение секретов

- Приватные ключи хранятся с правами только для пользователя агента.
- Если доступно системное хранилище ключей или ключ с аппаратной защитой, его
  СЛЕДУЕТ использовать.
- Секреты не попадают в журналы, дампы конфигурации и диагностический API.
- Агент поддерживает замену сертификата без замены ключа идентичности.
- Ротация ключа идентичности создаёт новый PeerId и считается миграцией узла.
- Мнемоническая фраза не входит в агент MVP; с ней работает отдельный
  вспомогательный процесс с явной процедурой резервного копирования и подтверждением
  оператора.

## 15. Наблюдаемость

Обязательные метрики:

- число соединённых и авторизованных пиров;
- размер таблицы маршрутизации;
- попытки подключения к начальным узлам и их результат;
- RTT ping по типу пути;
- успешные и неуспешные попытки пробивания NAT;
- активные резервирования ретрансляторов и переданный объём;
- отказы рукопожатия по классу причины без утечки секретов;
- версия служебного состояния, номер журнала C2 и возраст последних действительных
  записей.

Журналы содержат идентификатор корреляции и PeerId, но не открытую полезную
нагрузку, приватные ключи, полные сертификаты или шифротекст HPKE без
диагностической необходимости.

## 16. Поведение при отказах

- Установка соединения использует экспоненциально растущую задержку повторов со
  случайным разбросом и верхней границей.
- Потеря одного начального узла не прекращает работу с уже известными пирами.
- Потеря ретранслятора запускает резервирование на другом ретрансляторе.
- Неизвестное поле совместимой версии игнорируется только если схема помечает его
  необязательным.
- Неизвестная старшая версия идентификатора протокола отклоняется.
- При устаревшем состоянии отзывов узел переходит в явно наблюдаемый режим
  ограниченной работы; политику допустимых операций задаёт управляющий контур.
- Ошибка проверки подписи всегда приводит к безопасному отказу с запретом доступа.

## 17. Тестовая матрица

До завершения MVP нужны автоматические сценарии:

| Сценарий                               | Ожидаемый результат                                        |
|----------------------------------------|------------------------------------------------------------|
| Оба узла имеют публичный адрес         | Прямое соединение QUIC                                     |
| Один узел за NAT                       | Прямое соединение или пробивание NAT                       |
| Оба узла за разными NAT                | Пробивание NAT, при неудаче ретранслятор                   |
| Симметричный NAT                       | Резервный путь через ретранслятор                          |
| Начальный узел недоступен после поиска | Известные пиры продолжают общение                          |
| Ретранслятор недоступен                | Переключение на другой ретранслятор                        |
| Неверная подпись допуска               | Соединение закрыто до доступа к протоколам                 |
| Просроченный сертификат                | Соединение отклонено                                       |
| Сертификат отозван                     | Соединение отклонено после получения актуального состояния |
| Повтор сообщения                       | Полезная нагрузка не передана приложению повторно          |
| Несовместимая старшая версия           | Протокол отклонён с диагностируемой причиной               |

Тесты NAT должны выполняться не только в имитационной среде, но и в сетевых
пространствах имён с разными схемами отображения UDP-портов и правилами межсетевого
экрана.

## 18. Открытые решения

1. Выбрать набор алгоритмов HPKE после проверки межъязыковой поддержки; исходный кандидат —
   X25519 + HKDF-SHA-256 + ChaCha20-Poly1305.
2. Зафиксировать канонический профиль CBOR и формальные схемы конвертов и
   сертификатов.
3. Проверить поддержку QUIC, Noise, Circuit Relay v2, DCUtR и Kademlia выбранной Java-
   библиотекой при сборке GraalVM Native Image.
4. Задать TTL сертификатов, делегирований, записей пиров и окна защиты от повторов.
5. Определить профиль ёмкости начальных узлов и ретрансляторов, а также лимиты
   злоупотреблений.
6. Решить, нужен ли дополнительный предварительно распределённый сетевой ключ.
