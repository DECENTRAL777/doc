# Расклад

Общая архитектура децентрала. Статус: **проектирование overlay MVP**. Цель —
закрытая IPv4-сеть узлов с проверяемой идентичностью, защищённым обменом и поиском
пиров без обязательного центрального сервера после ввода узла в сеть.

## Слои и зависимости

```text
оператор: выдача/отзыв допуска
             │ подписанные сертификаты и список отзывов
             ▼
     доверенный UDP/Noise overlay
     ├─ защищённые соседские соединения, ACK, ping
     └─ Kademlia: PING, FIND_NODE
             │
             ├─ будущий C2
             ├─ будущее хранилище
             ├─ будущие обновления
             └─ будущий IPv6 VPN sidecar
```

Хранилище и C2 **независимо опираются на оверлей**. Хранилищу не требуется C2.
Порядок их реализации после готового P2P пока не утверждён. В отличие от старого
прототипа сеть не заявляет совместимости с libp2p, QUIC, GossipSub или gRPC.

## Компоненты

- **Агент**: единственный обязательный процесс на узле. В overlay MVP держит
  идентичность, сертификат, защищённые UDP-сессии, таблицу известных пиров и
  минимальную Kademlia. Не содержит веб-интерфейс или удалённую командную оболочку.
- **Операторский CLI**: вне сети агентов подписывает сертификаты и отзывы одним
  Ed25519 issuer-ключом. Приватный issuer-ключ не копируется на узлы.
- **Seed**: допущенный агент с известным IPv4:port для начального подключения;
  адрес seed сам по себе не даёт допуска. Рабочая конфигурация предусматривает
  несколько seed, но первый стенд может начинаться с одного.
- **Relay**: будущий допущенный узел, который пересылает пакеты конечной Noise-сессии
  без расшифрования содержимого. В первом LAN MVP не нужен.
- **Прикладные компоненты**: C2, хранение, обновление и IPv6 sidecar добавляются
  после проверки оверлея, каждый со своей политикой доступа.

## Идентификаторы и доверие

`network_id` — случайные 16 байт для логической сети. Узел имеет пару Ed25519 для
идентичности и отдельную пару X25519 для Noise. `NodeId` — 32-байтный
доменно разделённый SHA-256 от канонического Ed25519 public key; точное вычисление
указано в [Маляве](МАЛЯВА.md). Это **не** libp2p PeerId.

Единственный публичный ключ оператора установлен в trust bundle. Сертификат
связывает `network_id`, Ed25519/X25519 ключи, срок действия и серийный номер.
Завершается авторизация только после проверки сертификата и доказательства
владения ключами в Noise-рукопожатии. Известный адрес и найденный NodeId являются
подсказками маршрута, а не полномочиями.

Отзыв — подписанный список с монотонной версией. После получения более новой версии
отозванный пир не допускается к новым сессиям, уже установленные сессии закрываются.
Что делать при **устаревшем** списке из-за разделения сети, пока не решено; это не
скрытая гарантия непрерывной работы или безопасного отказа.

## Жизненный цикл узла

```text
без ключей → настроен → подключение к seed → авторизован → поиск пиров
                    ↘ отказ допуска/срока/подписи ↗
```

1. Узел локально создаёт ключи и получает от оператора сертификат и trust bundle.
2. Узел пробует IPv4:port известных seed с ограниченными повторами.
3. `Noise_XX_25519_ChaChaPoly_SHA256` устанавливается **между конечными узлами**.
   Они проверяют связь Noise-ключа с сертификатом и Ed25519 NodeId.
4. Только после авторизации открываются `PING`, `FIND_NODE` и другие overlay-сообщения.
5. Узел пополняет таблицу только идентичностями проверенных пиров. Потеря seed не
   разрывает уже установленные соединения.

Собственные бинарные сообщения, предел UDP-кадра и подтверждения определяет
[Малява](МАЛЯВА.md). UDP/Noise здесь не является упорядоченным байтовым потоком.

## Границы этапов

Первый gate — три узла в одной IPv4 LAN: два обычных узла знают адрес seed, но не
адрес друг друга; после авторизации они находятся через `FIND_NODE` и обмениваются
защищённым ping. Неверные сертификаты и повторы отвергаются. Далее — отдельный
gate для NAT и непрозрачного relay. Верхние подсистемы не должны заставлять
первый оверлей реализовывать большие блоки или общее состояние управления.

Текущий `agent/` с подписанной TCP shell-командой — отдельный опытный прототип из
`concept/`, не часть этой цепочки доверия и не wire format будущего C2.

## IPv6 sidecar

Планируемый виртуальный IPv6-адрес выводится из `network_id` и NodeId и
предоставляется sidecar-процессом VPN, который маршрутизирует данные через готовый
защищённый оверлей. Внутренний транспорт MVP остаётся IPv4/UDP. Конкретная
адресная формула, коллизии и разрешение IPv6 в NodeId — открытые решения sidecar,
не обещание первого релиза.
