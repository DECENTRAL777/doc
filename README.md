# Кронверкский децентрал им. Yimirs

Непубличная самоуправляемая сеть доверенных узлов. Проект объединяет P2P-оверлей,
распределённое хранилище, распределённый C2 и безопасное обновление агентов.

Статус проекта: проектирование. Документы описывают целевую архитектуру и границы
MVP; детали, которые ещё требуют прототипа или отдельного решения, явно отмечены.

## Цель

Узел должен после установки и выдачи оператором допуска:

1. восстановить свою криптографическую идентичность;
2. найти доверенные узлы и войти в закрытый P2P-оверлей;
3. установить связь с другим узлом при наличии NAT, используя ретранслятор как
   резервный маршрут;
4. получать проверяемое управляющее состояние и выполнять разрешённые адресные
   или массовые команды C2;
5. хранить и отдавать разрешённые данные;
6. безопасно обновлять агент без ручного копирования бинарников.

## Базовые принципы

1. **Закрытая сеть.** Знание адреса начального узла не даёт права
   участия. Каждый участник предъявляет действующий сертификат допуска.
2. **Криптографическая идентичность.** `PeerId` связан с ключом `Ed25519`.
   Ключ `X25519` используется отдельно для E2E-шифрования сообщений.
3. **Один оператор в MVP.** Оператор принимает и отзывает узлы. Корень доверия
   `ML-DSA-65` хранится автономно; повседневные полномочия делегируются
   ограниченным по сроку оперативным ключам.
4. **Децентрализованная доставка, не децентрализованная власть.** В MVP решение
   принимает один оператор, но управляющее состояние и команды C2 реплицируются и
   доставляются через сеть без обязательного центрального сервера на каждом чтении.
5. **Работа за NAT.** Предпочтительна прямая связь. Используются AutoNAT и
   пробивание NAT; если они не сработали, соединение остаётся через доверенный
   ретранслятор.
6. **Минимальный агент.** Агент не содержит веб-интерфейс и другие необязательные
   функции. Панель оператора, IPv6-интерфейс и восстановление из мнемонической
   фразы реализуются вспомогательными процессами.
7. **Проверяемые изменения.** Сертификаты, управляющие события, манифесты данных и
   релизы имеют подпись, версию и защиту от повторного применения.
8. **Отсутствие скрытого консенсуса.** Kademlia отвечает за поиск узлов, но не за
   принятие решений и не за строгую согласованность данных.

## Принятые решения

| Область                   | Решение для MVP                                                                         |
|---------------------------|-----------------------------------------------------------------------------------------|
| Сетевой стек              | Совместимые протоколы `libp2p`                                                          |
| Транспорт                 | QUIC; TCP с Noise как резервный вариант, если поддержан реализацией                     |
| Маршрутизация             | Закрытая Kademlia DHT с отдельным идентификатором протокола                             |
| Обход NAT                 | Circuit Relay v2, AutoNAT, DCUtR и пробивание NAT                                       |
| Идентичность узла         | `Ed25519`, представленный как `PeerId`                                                  |
| E2E-шифрование            | `X25519` через HPKE для сообщений, адресных команд и результатов                        |
| Операторский PKI          | `ML-DSA-65` по FIPS 204                                                                 |
| Модель доверия            | Один оператор, автономный корень и короткоживущие делегированные ключи                  |
| Распределённый C2         | Отдельный ключ; массовую команду видят все допущенные исполнители; результаты подписаны |
| Формат сообщений проекта  | Детерминированный CBOR, версионируемые структуры сообщений                              |
| Реализация агента на Java | JDK 25 и GraalVM Native Image                                                           |

## Компоненты

- **Агент** поддерживает идентичность, соединения, DHT, обмен сообщениями,
  локальное состояние и API для вспомогательных компонентов.
- **Операторский CLI** выдаёт и отзывает сертификаты, подписывает управляющие
  события и команды C2, собирает результаты и готовит релизы.
- **Начальный узел** даёт первоначальные адреса `multiaddr` известных участников,
  но не является источником полномочий.
- **Узел-ретранслятор** обеспечивает резервный маршрут для узлов без прямой
  связности.
- **Узел хранения** хранит зашифрованные контентно-адресуемые блоки.
- **Веб-панель** работает как вспомогательный компонент и общается с локальным
  агентом по gRPC.
- **Вспомогательный IPv6-компонент** предоставляет удобный локальный
  IPv6-интерфейс поверх оверлея.

Один процесс может совмещать несколько ролей. Право выполнять роль задаётся
сертификатом, а не параметром командной строки.

## План

1. **P2P-оверлей.** Авторизация и обнаружение узлов, проверка доступности, прямое
   соединение и резервный маршрут через ретранслятор.
2. **Распределённое хранилище.** Контентная адресация, манифесты, репликация,
   восстановление и сборка мусора.
3. **Распределённый C2.** Подписанный журнал событий и команд, адресное и массовое
   выполнение команд, снимки состояния, отзыв сертификатов и настройка ролей.
4. **Самообновляющийся агент.** Подписанные манифесты релизов, поэтапное
   развёртывание, проверка работоспособности и откат.
5. **Вспомогательные компоненты.** Веб-панель, алгоритмический IPv6 и
   восстановление ключей.

Каждый этап начинается после выполнения критериев предыдущего этапа. Подробные
критерии приведены в [Ходке](ХОДКА.md).

## Что не входит в MVP

- публичная или анонимная сеть;
- византийский консенсус между операторами;
- сокрытие метаданных и защита от глобального наблюдателя;
- обязательная постквантовая конфиденциальность пользовательского трафика;
- гарантия прямого соединения при любом NAT или межсетевом экране;
- хранение открытого текста на недоверенных узлах хранения;
- бесшовная ротация корня доверия без заранее подготовленной процедуры.

## Термины требований

Слова **ДОЛЖЕН**, **НЕ ДОЛЖЕН**, **СЛЕДУЕТ**, **НЕ СЛЕДУЕТ** и **МОЖЕТ** задают
нормативность требования в смысле RFC 2119/RFC 8174. Пока документ имеет статус
черновика, несовместимые изменения протокола допустимы только с увеличением его
версии.

## Правила внесения решений

1. Решение, влияющее на формат передачи, модель доверия или совместимость
   реализаций, сначала фиксируется в документации.
2. Неопределённое поведение помечается как открытый вопрос, а не описывается как
   гарантия.
3. Криптографические алгоритмы используются только по стандартному назначению:
   подпись не подменяет шифрование, хеш не подменяет MAC, транспортное шифрование
   не всегда подменяет E2E-шифрование.
4. Каждая гарантия безопасности должна иметь владельца ключа, процедуру ротации
   и поведение при компрометации.
